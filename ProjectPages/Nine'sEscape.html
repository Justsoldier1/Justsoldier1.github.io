Project Summary
This project was made for my first year Fundamentals of Game Development unit at my university. We had
free rein in this unit to create whatever project we wanted, and I decided I wanted to make a game
based off of the character Nine from my favourite book series that I was re-reading at the time,
called 'I am Number Four'.
The basic plan for the game was to create a robot replica of him, since I am better at hard surface
modelling, and allow the player to use his abilities to solve puzzles. The abilities were all
centered around gravity. The primary ability was switching gravity when touching walls, and the secondary
ability was being able to push and pull objects. These will be discussed in more detail
in the ‘Gravity system’ and ‘character abilities’ sections below.

Casting
A common problem I had to solve within this project was accessing information from a different class than the
one I was currently working in. Within Unreal engine, casting would normally be used here, but this can
cause high memory usage when used at a large scale. This wouldn't really have an impact on the performance
of my project, as there was not a lot of interaction occurring at once, but I wanted to use the more
optimised method, interfaces, so that I get in the habit of using them, which will ensure that my work on
larger projects in this future is as optimised as possible.

Another advantage of using interfaces is that they can be used with high level references. This means that
they are not linked to a single class and instead work with any actor that implements the interface
function. This helps stop my classes from being coupled together, which can help prevent unneeded dependencies. An
example of this is within the BP_Button actor. Instead of needing specific class types, it can just hold
a reference to linked classes that inherit the actor class, and attempt to call the interact function on them.
Using this method, if the linked actor does not have the correct function, instead of causing errors, the
function will just not be called.

Event based programming
A programming technique that I always attempt to avoid as much as possible is the tick / update technique.
This involves running certain checks, such as whether or not the player is grounded, every frame the game
runs. I avoid this technique as there are many much more effective methods to get the same effect, such as
overlap events or timers, without needing to run redundant or unnecessary code. For example, the gravity
direction UI element could get the direction of the wall in front of player every frame using a raycast, but
instead I have a capsule collision component facing out of the player, and when it overlaps with a wall, it gets
the gravity direction.
Gravity direction UI element:

For some use cases however, I need to check things very frequently. To do this, instead of using tick, I
instead use a timer that runs every 0.01 seconds. This emulates the accuracy of tick, but with the added
functionality of being toggleable, so I can stop it from running when it is not needed.

When creating a linear level based game such as this, it is important that the player’s progress is saved,
so that they do not need to restart from level 1 everytime they close the game. I had made a basic save system
before using game instances, but these only save variables while the game is running, and once the game closes all
data is destroyed.
Data is reset when the game is closed:

To fix this, I used a save game actor, which is a built in class within Unreal Engine that saves It's data to a file. To ensure I could
access this anywhere in the code, I saved a reference to it within the project's Game Mode actor, which can be accessed using the
GameplayStatics built in function: "GetGameMode". I then made an interface that allowed for me to set / get each SaveGame variable,
and save / delete the data in the current save slot.
Game mode interface functions:

This was not only used to lock players from entering levels that marked as unbeat, but also for saving the players best time to beat
the level. This was mainly inspired by a similar system in Ultrakill, as this system gave the game a lot more replayability, as the
player can try to beat the time, rather than just beating the level and never having a reason to revisit it. The system just looks
at the saved time, and the time of the level timer, and overwrites the saved time if the level timer has been running for less time.

The main mechanic of this project was the gravity system. The mechanic idea was inspired by the character Nine from 'I am Number Four'
by Pittacus Lore, while the functionality was inspired by the gravity fields in Super Mario Galaxy. The video below was my main
inspiration for how this mechanic would work.
"How spherical planets bent the rules in super mario galaxy" by Jasper:

At the start of the project, gravity fields where defined using collision box actors, but these were difficult to work with, and did
not allow for complex gravity changing collisions. The mesh shown below would be incredibly difficult to create gravity collisions
for, without them either being Janky, or providing the player with unexpected results.

I fixed this by creating a gravity field component that had a function that mimics the overlap event of the gravity field box
colliders. This means that it can be applied to any collider, such as a static mesh for more complex collisions. However, I used this as
little as possible, to avoid calculating complex collisions without needing to.

The code
The gravity fields use a parent for functionality, with each child selecting a different variable within the E_SelectedGravity enum.
This makes selecting gravity easier, as I can just select the gravity direction in blueprint, without needing to memorise gravity
direction and rotation vectors. For the gravity field component, the gravity direction enum is instance editable so that it can be
selected in world / per class for ease of use.
E_SelectedGravity enum:

This enum also meant that I could easily get the rotation of a gravity field in basic readable terms, so I used this to build a simple
UI element that tells the user what rotation a wall has.
Gravity direction UI element:

I can then use a switch statement to select different values needed for flipping gravity, such as the amount the camera needs to rotate
and the gravity direction, which is a vector that is built in to Unreal for flipping gravity. The camera rotation is needed as
gravity direction does not intrinsically change the camera view, just the direction the player falls.

This system also caused some issues with camera look and character movement code, so I had to move away from the standard unreal
movement methods. For the camera, I had to manually rotate it instead of using Unreal's built In functions. This also meant that for the
movement script I had to use the cameras forward and right vectors, instead of the actors, as the camera would be offset by the
move code.

Behaviour tree overview:


The AI enemy found in the final level of this project was created using a behaviour tree. This allows for the agent (the character
controlled by the AI) to select which 'branch' of code to run depending on the data held in the agent's blackboard.

The behaviour tree has two parent branches, which are FoundPlayer and NoPlayer. These both check whether the player variable is valid
within the blackboard, and runs the appropriate branch.
If the player is valid, the agent will move towards the player, and check to ensure that the player can still be seen. This is done
using the perception component, which is held within the AI controller. Then finally, if the player can still be seen, then a
projectile is shot at the agent's front facing arrow component.
Found player behaviour in game:

The NoPlayer parent branch is a bit more complicated, as I wanted specific conditions depending on the time between not seeing the
player. If the player has only recently not been seen, the agent will 'look for' the player. This is just done by rotating towards
it's two arrow components, which are placed at the agent's sides. I decided to make my own function that would rotate the agent over
time, as using the in built rotate to function looked strange.
Looking for recently lost player behaviour:
Within this project, I used basic procedural animations throughout every moving asset. I used these for two reasons, for one, to
compensate for my lack of experience within 3D animation. The other reason was to allow for accurate collisions with objects. For
example, the doors move in world when they open, so I did not need to do any other code to let the player move through an open door.

To make these animations, I used timelines, which are a blueprint functionality that allow for a variable, such as a position vector or
a multiply float, to be changed over a set period of time.
Whenever objects are spawned in this project, object pooling is used. This is a technique where objects are never despawned, but placed
outside of the players view, and stored. This means that when they are 'spawned' they are just moved to a position. This technique
helps save performance, as creating objects at runtime, especially at a large scale, can cause lag, while functionally providing
a similar result to object pooling.
